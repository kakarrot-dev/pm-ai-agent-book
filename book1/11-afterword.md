# 后记

Agent 让软件从“等待用户操作”走向“接受目标并采取行动”。这不是在原有产品上加一个聊天框，而是改变了产品与用户之间的责任关系。

一路读到这里，我们已经从两个看似简单的请求出发：替用户取消订阅，为员工找到可信的内部答案。它们最终牵引出场景、任务、边界、交互、能力、评估、安全、成本、运营和组织协作。Agent 产品的复杂性，正来自这些问题同时存在。

## 选择值得解决的问题

不是所有需求都值得 Agent 化。稳定路径可以交给工作流，只需要建议时应该保留 Copilot，需要可靠信息时先把搜索和知识治理做好。

产品经理的第一项责任，是抵抗“因为能做，所以要做”的冲动。用户价值、环境接入、结果验证、风险和单位经济性必须形成交集。越早放弃不成立的场景，团队越能把资源投入真正值得解决的问题。

## 定义自主边界

自主性不是产品成熟度的排名。读取资料、生成草稿、提交申请和接受金额方案，不应共享一个权限等级。

好的 Agent 产品会把自由留给需要理解与变通的地方，把确定规则交给工作流，把高风险决定交还给有权承担后果的人。它也会明确非目标，并在超出边界时可靠拒绝、降级或移交。

边界不是限制价值。边界让用户敢于委托，也让团队知道自己正在承诺什么。

## 让用户保持控制

用户把目标交给 Agent，并不等于放弃知情权和决定权。他需要理解系统怎样理解目标，准备做什么，正在等什么，哪些动作已经发生，最后凭什么宣称完成。

计划、状态、具体授权、暂停、恢复、人工接管和结果证据，共同构成 Agent 的产品界面。信任不是由拟人化语气产生，而是由一次次可预期、可纠正的交互积累。

## 用评估代替感觉

Agent 会变化，外部环境也会变化。一次成功演示无法证明产品可靠，一个平均分也不能掩盖严重风险。

评估要从业务结果延伸到任务完成、过程质量、用户体验、成本和风险。线上每一次真实失败，都应该被分类、归因，并在适合时变成回归用例。只有这样，模型、Prompt、知识、工具和工作流的改动才有共同判断标准。

## 对结果和风险负责

模型可能做出判断，工具可能执行动作，但产品责任不会因此消失。谁可以访问数据，谁批准高风险动作，什么算业务成功，事故怎样停止和恢复，仍然需要人和组织作出决定。

AI 产品经理不必独自掌握所有技术细节，却必须能够与设计、算法、工程、数据、安全、运营和业务专家共同定义这些责任。产品经理连接的不是一组功能，而是一套会行动的系统与现实世界之间的契约。

## 保持简单，也保持诚实

语音、Computer Use、多 Agent 和模型定制都会继续扩展 Agent 的能力。但复杂度只有在解决了已被证实的瓶颈时才有价值。

从一个任务闭环开始，先让结果可验证，让风险可控制，让失败可理解。等证据说明当前方案已经到达边界，再增加新的能力。这种节奏可能没有演示视频那么耀眼，却更接近一款能够长期存在的产品。

归根结底，AI 产品经理要反复回答四个问题：我们替谁解决什么问题，Agent 被允许做什么，怎样知道它做对了，以及出错时谁能够停止并负责。

技术会继续变化。只要这四个问题仍然清楚，产品就不会被技术名词带着走。
