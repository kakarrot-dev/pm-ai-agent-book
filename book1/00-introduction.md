# 引言

过去，产品经理设计一项功能，通常可以预先知道用户会看到什么、点击什么，系统又会返回什么。即使流程复杂，大部分路径仍由产品和工程团队事先写好。

Agent 改变了这个前提。用户不再只点击一个功能，而是把目标交给系统：“帮我取消这项订阅”“查清楚公司的差旅规则”“整理材料并提交审批”。系统需要理解目标、选择步骤、调用工具、读取反馈，并在过程中决定继续、求助还是停止。

这意味着产品经理正在定义一个新的产品参与者。它会判断，也会行动；能够处理没有被逐条写死的情况，也可能在不确定中做错。产品工作不再止于页面、功能和流程，还要回答：

- 什么问题值得交给 Agent；
- Agent 对什么结果负责；
- 它能看到什么，又有权做什么；
- 哪些决定必须保留给用户；
- 怎样证明任务真的完成；
- 如何评估不确定系统，而不是只看几次演示；
- 产品怎样在风险、成本和用户价值之间持续经营。

这本书就是围绕这些问题展开。

## 为什么需要产品经理视角

Agent 领域有大量技术概念：模型、上下文、记忆、知识库、工具、工作流、多 Agent、后训练。理解它们有价值，但只按技术模块学习，很容易知道“系统由什么组成”，却不知道“为什么值得做成产品”。

例如，长期记忆可以让 Agent 更了解用户，也可能保存了不该长期保留的临时信息；工具让 Agent 能够执行，也把错误从文字变成现实后果；多 Agent 可以隔离职责，也可能只增加成本和交接失败。

产品经理需要的不是把这些概念学得更浅，而是换一个问题顺序：先理解用户目标和业务结果，再决定哪些能力有必要；先定义自主边界和完成证据，再选择实现方式；先建立评估和风险门槛，再扩大产品范围。

技术在本书中不会消失。它会出现在真正影响产品选择的位置，并回答五个问题：解决什么用户问题，何时值得采用，会引入什么风险，需要付出什么成本，以及如何验证有效。

## 两类 Agent，贯穿同一条产品生命周期

全书使用两条虚构案例。案例中的流程和数据用于解释方法，不代表某个真实企业或真实用户。

### 客户服务与事务办理 Agent

第一条案例帮助用户取消订阅、申请标准退款，并在必要时处理外部等待和异常。它代表一类需要替用户进入外部系统、与其他参与者沟通并对结果负责的 Agent。

这类产品的难点不在于生成一段回复，而在于长流程执行、金钱与权益、用户授权、外部变化和结果验证。它让我们看到，自主性怎样创造价值，也怎样放大责任。

### 企业知识与办公 Agent

第二条案例帮助员工检索内部知识、形成有来源的回答，并逐步扩展到材料生成和受控流程。它代表一类嵌入组织信息、权限和协作关系的 Agent。

这类产品的难点是知识可信度、版本时效、权限隔离和组织责任。它提醒我们，能够回答不等于有权回答，内容看起来合理也不等于被证据支持。

两条案例会经过相同的产品生命周期，却不会被强行做成同样的产品。事务 Agent 首期包含受控执行，企业知识 Agent 首期主要交付有来源的辅助。比较它们，正是为了说明产品方法如何在不同风险结构中作出不同选择。

## 全书怎样展开

第一篇回答“什么值得做”。第 1 章区分聊天机器人、Copilot、工作流和 Agent；第 2 章从价值、接入、验证、风险和成本筛选场景；第 3 章把需求拆成包含参与者、异常、状态和证据的任务模型。

第二篇回答“应该做成什么”。第 4 章定义 MVP、自主等级和人工介入；第 5 章设计计划、进度、授权、暂停、恢复和接管；第 6 章再把产品需求映射到模型、知识、记忆、工具、工作流和多 Agent。

第三篇回答“怎样证明有效并安全经营”。第 7 章建立业务、任务、体验、成本和风险评估；第 8 章处理错误行动、权限、隐私、提示注入和单位经济性；第 9 章把线上失败转成可验证、可发布的持续改进。

第四篇回答“何时继续扩展”。第 10 章讨论语音、Computer Use、多 Agent 和模型定制的采用条件，以及产品、设计、算法、工程、安全、数据、运营和业务专家如何共同负责。

## 怎样阅读这本书

如果你正在从传统产品转向 AI 产品，建议按顺序阅读。前六章建立 Agent 产品的核心工作方法，后四章把它推向上线和规模化。

如果你已经在做 Agent，可以从当前问题进入：场景太多时看第 2 章，边界不清时看第 4 章，用户不信任时看第 5 章，团队总在争论技术方案时看第 6 章，迭代依赖感觉时看第 7 和第 9 章。

每章都有检查表、画布或模板。它们不是标准答案，而是帮助团队暴露尚未回答的问题。一个评分卡不会替你决定场景，一个架构图也不会替你承担结果。

书中使用 Mermaid 流程图、架构图和状态图解释抽象关系，也会用少量代码块展示 Prompt、结构化输入输出和产品协议。它们服务于理解，不要求读者搭建工程环境。

## 本书的核心主张

Agent 产品经理最重要的能力，不是记住最多技术名词，而是持续做出边界清楚、证据充分的判断。

一个值得上线的 Agent，不是因为它看起来最自主，而是因为它解决了真实问题；在授权范围内行动；知道何时停下；能够用证据说明结果；并且团队有能力评估、治理和长期经营它。

接下来，我们先从最基础、也最容易被混淆的问题开始：用户需要的究竟是一次回答、一位副驾驶、一条自动流程，还是一个对结果负责的 Agent？
